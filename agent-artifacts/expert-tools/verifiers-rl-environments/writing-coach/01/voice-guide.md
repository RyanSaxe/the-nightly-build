# Voice guide: verifiers RL environments (expert-tools, 01)

## How this piece should sound

The piece is written by a practitioner who has installed the current verifiers
release, read its source, and built one environment with it. It speaks to
peers: people who already know what a policy gradient, a rollout and a held-out
score are, and who will copy the listings into their own editor. Nothing
about RL in general needs explaining to them. What they lack is the verifiers
interface, and the specific ways a macro-nowcasting task can hand the agent the
answer. Plain first person is right wherever it reports something actually
done, such as a package installed, a listing run or a signature read from the
source. Karpathy's training paragraph and Mody's check against the official
GPT-2 code show the register: what ran, on what, and what it printed, with no
claim larger than the run. This commission says the environment was not
trained, so the same plainness applies to the smaller set of things that were
executed or checked.

The interface is the subject, and Mody's handling of the gpt2 signature shows a
way to teach one. He puts the function header on the page and says what each
argument is before he fills in the body. The verifiers pieces this article
builds (the TaskData subclass, Taskset.load, Task.setup, the Toolset, the
reward and metric functions, the CLI) may be taught the same way, with each
hook's signature from the installed release ahead of the code that fills it.
Where verifiers offers more than one place to put something, such as a value
that could be state, a tool, a metric or part of the reward, Yang's passage on
wrapper classes shows a single test that decides between them, applied to one
real case. Use such a test where the source or the design supports one. Yang's
three-operators passage shows the other half of an interface: naming every
identifier a contributor ends up owning, and saying which one does the work.

Leakage in this task is concrete, and Mody's causal-mask passage shows how a
leak reads when it is shown with one actual input: a named token sees a named
future token, and the consequence follows in a sentence. The vintage, lookahead
and sandbox paths the commission names may each read better at that grain,
with one series and one as-of date, than as a general warning. The researcher
supplies the instance. Rollout cost may call for Horace He's approach in the
calculator passage: published figures, the arithmetic between them, and a plain
statement of what the result means for the reader's own run. His overhead test
gives the reader one cheap check that tells them which case they are in, which
is the kind of thing a reader deciding whether to adopt verifiers can use.

Maintenance and drift belong in the same plain voice. Yang marks a slide as
about to go stale and names the work that will change it, which is how a writer
can handle a docs site that describes a different API from the PyPI release, or
a harness id that changed between versions, without editorializing about the
project. Karpathy's closing note states the cost of the method he has just
taught, as operational facts, and an expert-tools reader needs that weighed
statement about adoption cost.

The exemplars come from personal blogs, and some of their best-known marks
belong there: Mody's "It works!!!", Horace's "brrrr", Karpathy's exclamation
points. A press article may carry a dry aside where it rides on the subject's
own nouns, like Karpathy's "because meh" about missing biases, and should leave
the rest. The owner's rule bans em-dashes and semicolons. Yang's operator
passage turns on a semicolon and Horace's prose often uses a spaced hyphen as a
dash. In both cases a period carries the same content, and that is the
substitution to make.

## Edward Z. Yang, "PyTorch internals"

Source: https://blog.ezyang.com/2019/05/pytorch-internals/

> "There's one last way you can make an "extension" to Tensor functionality, and that's write a wrapper class around PyTorch tensors that implements your object type. This perhaps sounds obvious, but sometimes people reach for extending one of the three parameters when they should have just made a wrapper class instead. One notable merit of wrapper classes is they can be developed entirely out of tree.
>
> When should you write a tensor wrapper, versus extending PyTorch itself? The key test is whether or not you need to pass this tensor along during the autograd backwards pass. This test, for example, tells us that sparse tensor should be a true tensor extension, and not just a Python object that contains an indices and values tensor: when doing optimization on networks involving embeddings, we want the gradient generated by the embedding to be sparse."

Checked: https://blog.ezyang.com/2019/05/pytorch-internals/ (raw HTML via curl), retrieved 2026-10-14
Yang lays out two ways to extend a library and gives one test that picks between them, then runs the test on a real case so the reader sees it decide something. The maintainer is visible in "sometimes people reach for", which reports a mistake he has seen contributors make. The question in the second paragraph is answered in the next sentence.

> "One important thing to be aware about when writing operators in PyTorch, is that you are often signing up to write three operators: abs_out, which operates on a preallocated output (this implements the out= keyword argument), abs_, which operates inplace, and abs, which is the plain old functional version of an operator.
>
> Most of the time, abs_out is the real workhorse, and abs and abs_ are just thin wrappers around abs_out; but sometimes writing specialized implementations for each case are warranted."

Checked: https://blog.ezyang.com/2019/05/pytorch-internals/ (raw HTML via curl), retrieved 2026-10-14
Every function the contributor will own is named by its exact identifier, with a clause saying what each one is for, and the second sentence says which one does the real work. "Signing up to write" is a maintainer describing a cost the API puts on its users. The second sentence depends on a semicolon, which this article cannot use, and a period before "but" leaves the content intact.

> "This is yet another slide which will hopefully be out of date in the near future. Will Feng is working on a Variable-Tensor merge in C++, following a simple merge which happened to PyTorch's frontend interface."

Checked: https://blog.ezyang.com/2019/05/pytorch-internals/ (raw HTML via curl), retrieved 2026-10-14
Yang flags part of his own explanation as about to go stale and says who is changing it and how. A reader months later can tell which parts of the picture to distrust. The tone is matter-of-fact, with no apology and no complaint about the codebase.

## Andrej Karpathy, "Deep Reinforcement Learning: Pong from Pixels"

Source: https://karpathy.github.io/2016/05/31/rl/

> "Suppose we're given a vector x that holds the (preprocessed) pixel information. We would compute:
>
> ```
> h = np.dot(W1, x) # compute hidden layer neuron activations
> h[h<0] = 0 # ReLU nonlinearity: threshold at zero
> logp = np.dot(W2, h) # compute log probability of going up
> p = 1.0 / (1.0 + np.exp(-logp)) # sigmoid function (gives probability of going up)
> ```
>
> where in this snippet W1 and W2 are two matrices that we initialize randomly. We're not using biases because meh. Notice that we use the sigmoid non-linearity at the end, which squashes the output probability to the range [0,1]. ... Now, the initial random W1 and W2 will of course cause the player to spasm on spot. So the only problem now is to find W1 and W2 that lead to expert play of Pong!"

Checked: https://karpathy.github.io/2016/05/31/rl/ (raw HTML via curl), retrieved 2026-10-14
Four lines of numpy, each with a comment, and then prose that uses the same variable names as the code, so the reader moves between the two without translating. "Because meh" admits a simplification in one word and moves on. The last sentence restates the whole training problem in terms of the two matrices just defined.

> "I implemented the whole approach in a 130-line Python script, which uses OpenAI Gym's ATARI 2600 Pong. I trained a 2-layer policy network with 200 hidden layer units using RMSProp on batches of 10 episodes (each episode is a few dozen games, because the games go up to score of 21 for either player). I did not tune the hyperparameters too much and ran the experiment on my (slow) Macbook, but after training for 3 nights I ended up with a policy that is slightly better than the AI player. The total number of episodes was approximately 8,000 so the algorithm played roughly 200,000 Pong games (quite a lot isn't it!) and made a total of ~800 updates."

Checked: https://karpathy.github.io/2016/05/31/rl/ (raw HTML via curl), retrieved 2026-10-14
The paragraph reports what was run, on what hardware, for how long, and how good the result was, and the claim ("slightly better than the AI player") is no larger than the run supports. The counts of episodes, games and updates let the reader size the cost without being told it was expensive. Karpathy is present in "my (slow) Macbook" and in the aside about how many games that is.

> "As a last note, I'd like to do something I wish I had done in my RNN blog post. I think I may have given the impression that RNNs are magic and automatically do arbitrary sequential problems. The truth is that getting these models to work can be tricky, requires care and expertise, and in many cases could also be an overkill, where simpler methods could get you 90%+ of the way there. The same goes for Policy Gradients. They are not automatic: You need a lot of samples, it trains forever, it is difficult to debug when it doesn't work."

Checked: https://karpathy.github.io/2016/05/31/rl/ (raw HTML via curl), retrieved 2026-10-14
Karpathy corrects an impression his own earlier post left, then states the cost of the method he has just spent the post teaching. The costs are operational and specific to the work (samples, training time, debugging). The person is visible in the admission about the RNN post, which is about his own writing.

## Jay Mody, "GPT in 60 Lines of NumPy"

Source: https://jaykmody.com/blog/gpt-from-scratch/

> "The gpt2 function is the actual GPT code we'll be implementing. You'll notice that the function signature includes some extra stuff in addition to inputs:
>
> - wte, wpe, blocks, and ln_f are the parameters of our model.
> - n_head is a hyperparameter that is needed during the forward pass."

Checked: https://jaykmody.com/blog/gpt-from-scratch/ (raw HTML via curl), retrieved 2026-10-14
Mody puts the signature on the page before any body exists and accounts for every argument in it, sorted into parameters and hyperparameters. The reader knows what each name is before the code uses it. "Some extra stuff" is a casual phrase, and the list after it is exact.

> "There is a bit of an issue with our current self-attention setup, our inputs can see into the future! For example, if our input is ["not", "all", "heroes", "wear", "capes"], during self attention we are allowing "wear" to see "capes". This means our output probabilities for "wear" will be biased since the model already knows the correct answer is "capes"."

Checked: https://jaykmody.com/blog/gpt-from-scratch/ (raw HTML via curl), retrieved 2026-10-14
The leak is shown with a specific input, a specific token and the specific future token it can see, and the consequence follows in one sentence. The same five-token example has run through the whole post, so the reader already knows it. The first sentence is a comma splice, which the house standard would split into two sentences.

## Horace He, "Making Deep Learning Go Brrrr From First Principles"

Source: https://horace.io/brrr_intro.html

> "For example, if we perform x.cos().cos(), usually we need to perform 4 global reads and writes.
>
> ```
> x1 = x.cos() # Read from x in global memory, write to x1
> x2 = x1.cos() # Read from x1 in global memory, write to x2
> ```
>
> But, with operator fusion, we only need 2 global memory reads and writes! So operator fusion will speed it up by 2x.
>
> ```
> x2 = x.cos().cos() # Read from x in global memory, write to x2
> ```
>
> Much better."

Checked: https://horace.io/brrr_intro.html (raw HTML via curl), retrieved 2026-10-14
The smallest possible example carries the concept, and the comment on each line counts exactly the quantity the paragraph is about. The 2x follows from counting reads and writes, so the reader can redo it. "Much better" is a two-word verdict after the evidence.

> "When it come to reasoning about whether your operation is memory-bandwidth bound, a calculator can go a long way.
>
> For simple operators, it's feasible to reason about your memory bandwidth directly. For example, an A100 has 1.5 terabytes/second of global memory bandwidth, and can perform 19.5 teraflops/second of compute. So, if you're using 32 bit floats (i.e. 4 bytes), you can load in 400 billion numbers in the same time that the GPU can perform 20 trillion operations. Moreover, to perform a simple unary operator (like multiplying a tensor by 2), we actually need to write the tensor back to global memory.
>
> So... until you're doing about a hundred operations in your unary operator, you'll be spending more time performing memory accesses than actual compute."

Checked: https://horace.io/brrr_intro.html (raw HTML via curl), retrieved 2026-10-14
He starts from two published hardware figures, shows the division between them, and ends on a threshold the reader can apply to their own code. Every step is arithmetic a reader can check. "A calculator can go a long way" is the voice of someone who prefers estimating to guessing.

> "So, how do you tell if you're in this regime? Well, since overhead generally doesn't scale with problem size (while compute and memory do), the easiest way to tell is to simply increase the size of your data. If that doesn't increase the runtime proportionally, you're overhead bound. For example, if you double your batch size but your runtime only increases by 10%, you're likely overhead bound."

Checked: https://horace.io/brrr_intro.html (raw HTML via curl), retrieved 2026-10-14
The question is answered at once with a test the reader can run in a minute, followed by the reason it works and a numeric example. The person is in "Well," and in the hedge "likely", which is attached to a specific number. Elsewhere in this piece He uses a spaced hyphen as a dash, which this article replaces with a period.
