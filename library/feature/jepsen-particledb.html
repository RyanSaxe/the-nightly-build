Jepsen finds ParticleDB’s default mode losing committed writes among 96 issues

In versions 1.1.4 through 1.1.17 of ParticleDB, advertised as “Full ACID. 159K TPS.”, WHERE 4 = 5 returned the row with primary key 5.

5 min read2026-11-01

Guarantees tested one node at a time

Orkes advertised ParticleDB, a Postgres-compatible database, as “Full ACID. 159K TPS.” and as “formally proven” with TLA+, wording that Jepsen’s report quotes from the home page.1 On 2026-10-31 Jepsen reported 96 issues from tests of versions 1.1.4 through 1.1.18.11.rc-22 and wrote that the Full ACID claim was “somewhat premature.” The default transaction mode, occ, lost committed writes in normal operation. The TLA+ claim could not be checked, because no specification was available.1

Orkes, the vendor, funded the analysis, which Jepsen says it conducted under its ethics policy. Every test ran on a single node, because the builds Orkes supplied did not support replication.1

Four of six claims met a measured failure

Each row is one advertised guarantee, in the words the report prints, and each cell to its right is what Jepsen recorded against it. Orkes has since rewritten the home page and documentation pages the report quotes, so the report is now the record of that wording.1

“Jepsen-safe” was Orkes’s own label. Jepsen printed it and wrote that, since it evaluates safety against documentation and marketing claims, it was not clear how to interpret the term.1

WHERE 4 = 5 returned the row with primary key 5

Jepsen’s example is a table t with columns a, the primary key, and b, holding rows 4 | 5 and 5 | 6. In versions 1.1.4 through 1.1.17, ParticleDB “aggressively interpreted WHERE something = x as a primary-key lookup of x, regardless of the value of something.”1 The query in the diagram therefore asked for key 5 and never compared the 4.

The example is a single statement with no concurrent transaction. Version 1.1.18.4 stopped treating every equality as a key lookup. A related fault appeared only inside a transaction: in 1.1.4 through 1.1.18.8, SELECT * FROM t WHERE TRUE returned no rows (#35), and it seemed improved in 1.1.18.9.1

Ten issues survived to rc-22

Jepsen wrote that by 1.1.18.11.rc-22 all but ten of the 96 issues appeared resolved.1 The chart places seven findings on the builds Jepsen tested, four of them among the ten. A bar spans the builds where the behavior appeared, and a bar that reaches rc-22 was still open when testing ended.

Stale read, the behavior behind #109, is a read that fails to observe an earlier completed write, which strict serializability forbids.7 Jepsen saw it roughly every 300,000 transactions at rc-18. Process kills produced Lost Update under the same mode (#107).1

Jepsen has not evaluated any build after rc-22. It recommended that users halt further deployment of ParticleDB and migrate to other databases as soon as possible. Orkes told Jepsen the issues likely came from an extensive refactor in spring 2026 and that customers who stayed on an earlier version were likely unaffected.1 Orkes’s own post says: “As of ParticleDB 1.1.19, we report that all identified issues have been addressed.”8 Jepsen’s report names the build as 1.1.19-rc.13.
